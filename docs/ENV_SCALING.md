# num_envs 바꾸기

**결론**

```
num_envs                4096
max_gpu_contact_pairs   32M          (기본 8M)
spawn                   60 m 격자 흩뿌림
minibatch_size          32768        (num_envs 와 같은 배수)
GPU 당 잡 수             1            (조건이 8개 넘을 때만 2)
그대로 두는 것            default_buffer_size_multiplier 10, num_threads 4, substeps 2
```

2048 대비 1.31배 빠르고 PhysX 경고가 없다. 8192는 **더 느리다** — 깨끗하게 돌리려면
128M 버퍼가 필요한데, 그 버퍼 자체가 처리량을 28 % 깎기 때문이다.

```bash
python scripts/env_config.py 4096                    # 같이 바뀌어야 하는 값
python scripts/env_config.py 4096 --samples 393e6    # + 같은 학습량 맞추는 iteration
python scripts/env_config.py 4096 --apply runs/gen_cfgs/steer/f2.yaml
```

세 레포(`TokenHSI-steer`, `TokenHSI-ma`, `TokenHSI`) 모두 같은 rl_games / IsaacGym 스택이라
1~3절 규칙은 공통이다. 4절의 실측값은 씬마다 다르므로 레포별로 다시 재야 한다.

## 1. minibatch_size 는 num_envs 와 같은 배수로 움직여야 한다

rl_games는 **한 번 데이터를 모은 뒤 그 배치로 여러 번 연속 업데이트**한다.

```
batch          = num_envs × horizon_length
연속 업데이트 수 = (batch / minibatch_size) × mini_epochs
```

num_envs만 올리면 같은 롤아웃으로 더 많이 밟게 되고, 마지막 업데이트는 그만큼 낡은
정책이 모은 데이터를 쓴다. PPO 클리핑이 스텝 하나는 막지만 누적 드리프트는 막지 않는다.
**minibatch를 같은 배수로 올리면 연속 업데이트 수가 유지되고, 바뀌는 건 업데이트당
기울기 노이즈가 낮아진 것뿐이다.** 그게 "학습은 같고 wall-clock만 줄어드는" 조건이다.

| num_envs | minibatch | 연속 업데이트 | |
|---|---|---|---|
| 2048 | 16,384 | 24 | 기준 |
| 4096 | 16,384 | 48 | **다른 학습** |
| 4096 | 32,768 | 24 | 등가 |
| 8192 | 65,536 | 24 | 등가 |

`batch % minibatch_size == 0`은 rl_games의 assert다. 2의 거듭제곱이면 항상 만족한다.
(256 env로 돌리려다 여기서 죽은 적 있다: 256×32=8192 < 16384.)

## 2. learning_rate

minibatch가 커지면 노이즈가 √배로 준다. lr을 올릴 여지가 생기지만 **필수는 아니다.**
`env_config.py`는 기본으로 √스케일을 제안한다. 확신이 없으면 `--lr-rule none`으로
기준값을 유지하고 슬롯 하나를 lr 비교에 쓰는 게 안전하다.

## 3. 같은 학습량 맞추기

epoch 수가 아니라 **총 샘플 수**가 기준이다.

```
총 샘플 = num_envs × horizon_length × iterations
2048 × 32 × 6000 = 3.93억
4096 × 32 × 3000 = 3.93억     ← 같은 학습량, iteration 절반
```

## 4. 실측 — 손잡이는 두 개뿐이고, 둘 다 처음엔 잘못 짚었다

### 원인 ①: spawn 이 한 점에 몰려 있었다 (우리가 만든 버그)

IsaacGym은 **모든 env를 하나의 물리 씬에 넣는다.** TokenHSI는 `envSpacing: 0`으로 env를
전부 world 같은 자리에 만들고 `col_group = env_id`로 충돌만 필터링한다. 물리적으로는
무해하지만 **GPU broadphase는 겹치는 모든 AABB 쌍을 계속 추적한다.**

steer의 평지 스텁 `_FlatTerrain.sample_valid_locations`가 **zeros를 반환**하고 있었다.
리셋마다 humanoid N명이 원점 한 점에 겹쳐 섰고, 그게 broadphase 요구량을 22배로 키웠다.

```
4096 원점집중 → 510,856,011 필요
4096 흩뿌림   →  23,586,348 필요
```

**증거**: 공식 stage2 terrain carry 런은 같은 2048 env에서 경고가 0건이다(실제 지형이
캐릭터를 흩뿌린다). 우리 steer 런은 175개 로그 중 79개에서 경고가 떴다.

`_FlatTerrain`이 이제 env를 60 m 격자로 흩뿌린다(`STEER_CELL`). 실측 확인: 이웃까지
중앙값 60.0 m, **10 m 이내에 이웃이 있는 env 0/2048**. 태스크는 전부 상대 좌표라 동작은 동일.

### 원인 ②: 손잡이는 `max_gpu_contact_pairs` 다 (배수가 아니다)

`default_buffer_size_multiplier`를 10 → 40 → 200 → 1000 → 5000 으로 500배 올려도
8192의 요구량이 95.2 M에서 **한 톨도 안 변했다.** 반면 `max_gpu_contact_pairs`를 올리자
곧바로 경고가 사라졌다. 처음에 둘을 **동시에** 바꿔놓고 분리를 안 해서 한참 헤맸다.

IsaacGym Preview 4가 노출하는 PhysX 손잡이는 이 둘뿐이다
(`gymapi.PhysXParams` 직접 확인). `foundLostAggregatePairsCapacity`를 직접 여는 API는 없다.

### 원인 ③: 버퍼가 크면 느려진다 — 이게 8192를 죽인다

```
4096 + 32M  : 34,956 fps   경고 0
4096 + 128M : 25,199 fps   경고 0      ← env 같음, 버퍼만 4배 → 28 % 느림
8192 + 128M : 25,478 fps   경고 0
```

**대조군 `4096 + 128M`이 원인을 갈랐다.** 8192가 느린 건 env 수 때문이 아니라
큰 버퍼 때문이다. 그리고 8192는 32M/64M 에서 경고가 뜨므로(요구 ~95 M) **128M 이 필수**다.
빠져나갈 길이 없다.

### 격자 실측 (steer carry, 흩뿌림 60 m, 14 iteration, 통과 = rc 0 그리고 warn 0)

| num_envs | contact pairs | 배수 | warn | fps | |
|---|---|---|---|---|---|
| 2048 | 8M (기본) | 10 | **0** | 26,652 | 통과 |
| 4096 | 16M | 10 | 2 | 36,070 | 요구 24.0 M |
| **4096** | **32M** | **10** | **0** | **34,956** | **통과 · 최적** |
| 4096 | 32M | 40 | 0 | 34,524 | 배수는 무관 |
| 4096 | 128M | 10 | 0 | 25,199 | 버퍼 과다 → 28 % 손해 |
| 8192 | 32M | 10 | 2 | 36,908 | 요구 96.4 M |
| 8192 | 64M | 10 | 2 | 24,152 | 요구 94.7 M |
| 8192 | 128M | 10 | **0** | 25,478 | 통과, 그러나 4096보다 느림 |
| 8192 | 512M | 40 | — | — | 호스트 pinned 메모리 실패 |
| 16384 | 128M | 10 | 2 | 22,059 | 요구 381 M |
| 16384 | 512M | 40 | — | — | 호스트 pinned 메모리 실패 |

간격은 60 m로 충분하다. 300 m로 벌려도 요구량이 안 변한다 (4096: 23.6M → 23.9M).

요구량은 흩뿌린 뒤에도 **env 수의 제곱**으로 늘어난다 — 4096 24.0 M, 8192 95 M, 16384 381 M.
381 M을 덮으려면 512M 버퍼가 필요한데 그건 호스트 pinned 메모리에서 죽는다. **깨끗하게 돌릴 수 있는 최대는 8192이고, 가장 빠른 것은 4096이다.**

### 처리량과 정확성은 이 축에서 맞바꿈이다

경고가 뜨는 설정이 **더 빠르다** (4096@16M 36,070 > 4096@32M 34,956;
8192@32M 36,908 > 8192@128M 25,478). 접촉을 버리니까 빠른 것이다.
**`rc=0`은 통과 조건이 아니다. `warn=0`이 조건이고, fps 는 그 다음이다.**
한때 "8192가 1.69배 빠르다"고 적었던 수치는 전부 경고가 뜬 런의 것이라 무효다.

### 안 통하는 손잡이: PhysX 스레드

`num_threads`를 4 → 32 → 64 → 128 로 올리면 **단조롭게 느려진다**
(34,778 → 29,326 → 26,729 → 23,071, GPU 사용률도 40 %→30 %). 224코어 머신이지만
CPU 병렬화는 병목이 아니다. TokenHSI 기본값 4를 그대로 둔다.

### soak

`4096 + 32M + 흩뿌림`으로 400 iteration 연속 학습: **경고 0, 에러 0.**
(14 iteration 통과는 8시간 통과의 근거가 못 되므로 후보는 반드시 소킹한다.)

## 5. 손잡이가 있는 곳

| 설정 | 위치 |
|---|---|
| `num_envs` | 커맨드라인 `--num_envs` |
| `minibatch_size`, `mini_epochs`, `horizon_length`, `learning_rate` | `tokenhsi/data/cfg/train/rlg/*.yaml` |
| **`max_gpu_contact_pairs`** (기본 8M) | `tokenhsi/utils/config.py:203`. env cfg의 `sim.physx` 섹션이 덮어쓴다. steer 4096용은 `amp_humanoid_steer_carry_cp32.yaml` |

| spawn 분산 간격 | `STEER_CELL` (기본 60 m) |

## 6. 레포별 상태

| 레포 | envSpacing | spawn | 경고 |
|---|---|---|---|
| `TokenHSI-steer` | 0 | `_FlatTerrain` 60 m 격자 (수정 완료) | 4096까지 0 |
| `TokenHSI-ma` | 5 | multi_task env, 지형 스캐폴딩 없음 | 로그 0 — **단 num_envs 128 에서만** |
| `TokenHSI` (원본) | — | 실제 terrain 메시 | 0 |

### ma 실측 (2026-08-17, A=1) — **접촉쌍이 제약이 아니다**

`scripts/ma/train.sh` 로 12점을 쟀다. **전부 warn=0** 이다:

| num_envs | 재본 contact pairs | warn |
|---|---|---|
| 2048 | 4M · 8M | 0 |
| 4096 | 1M · 8M · 16M · 32M | 0 |
| 8192 | 32M · 128M | 0 |
| 16384 | 128M | 0 |

**1M 은 양성 대조군으로 넣은 것이다** — 터무니없이 작으니 반드시 넘쳐야 한다고 봤는데
60 iteration 을 돌고도 안 넘쳤다. `max_gpu_contact_pairs` 는 gymutil 파싱 목록에 있고
생성된 cfg 에도 값이 들어가 있으니 적용은 되고 있다. 즉 **ma 씬의 요구량이 진짜로
1M 미만**이다. `envSpacing` 을 0 으로 (env 원점을 전부 겹치게) 해도 안 넘쳤다.

> **양성 대조군을 안 넣었으면 "8M 이면 되네" 하고 지나갔을 것이다.** 통과하는 것만
> 보면 "안 뜨는 것"과 "못 잡는 것"을 구분할 수 없다. 새 측정에는 반드시 실패해야 하는
> 점을 하나 넣는다.

### (해결됨) steer 와 ma 의 요구량이 30 배 달랐던 이유 — `envSpacing`

```
steer   4096 · 무한 평면 · 60 m 흩뿌림   →  요구 24.0 M   (env 당 ~5,900 짝)
ma      4096 · 무한 평면 · 10 m 격자     →  요구 < 1 M    (env 당 ~200 짝 미만)
```

**더 넓게 흩뿌린 쪽이 30 배 더 필요하다.** 후보를 하나씩 제거했다:

| 후보 | 확인 결과 |
|---|---|
| 지면이 다르다 (메시 vs 평면) | **아니다.** `HumanoidSteerCarry._create_ground_plane` 이 부모의 trimesh 를 오버라이드해 `Humanoid._create_ground_plane`(해석적 평면)을 부른다. `_FlatTerrain` 은 지형 *객체*만 대체하는 스텁이다. 뷰어에서 평면으로 보이는 게 맞다 |
| 간격이 다르다 | **아니다.** steer 가 오히려 6 배 넓다 (60 m vs 10 m). ma 를 간격 0 으로 해도 안 넘친다 |
| 액터 수가 다르다 | **아니다.** `create_actor` 호출 지점이 steer 6 · ma 8 로 ma 가 더 많다 |
| 측정이 짧았다 | **아니다.** 14 → 60 iteration 으로 늘려도 동일 |

**답은 `envSpacing` 이었다.** steer 는 `envSpacing: 0` 이라 4096 env 의 원점이 전부
world 원점에 겹친다. `_platform_default_pos` 가 생성 시점의 env 원점이므로, 선반을 안 쓰는
env 가 리셋마다 플랫폼을 **한 점에 주차**한다.

```
플랫폼 4096 + 타겟 플랫폼 4096 = 8,192 개가 한 점에
짝 = 8192 × 8191 / 2 ≈ 33.5 M   (전부 주차 시 상한)
실측 요구       22.6 M           ← 자릿수 일치
```

ma 는 `envSpacing: 5` 라 주차된 플랫폼도 각자 격자 칸에 놓여 안 겹친다. 그래서 30 배 차이가
났다. `_FlatTerrain` 은 **캐릭터**만 60 m 로 흩뿌렸고 플랫폼은 그 목록에서 빠져 있었다.

> **한 단계 위에서 봤어야 했다.** 흩뿌림(`STEER_CELL`)을 아무리 넓혀도 안 듣던 이유가
> "흩뿌림 대상에 플랫폼이 없어서" 였다. 노브를 돌려보기 전에 **무엇이 그 노브를 안 받는지**
> 를 먼저 셌어야 한다.

> **상속 체인에서 한 단계만 보고 판단하지 않는다.** 부모의 `create_training_ground` 를
> 보고 "steer 는 지형 메시를 쓴다"고 결론냈다가 자식이 그걸 덮는 걸 놓쳤다.
> 사용자가 "뷰어에선 평면이던데" 라고 짚어서 잡혔다. **관측이 코드 추론을 이긴다.**

## 7. GPU 당 잡 수

한 잡은 GPU를 다 못 쓴다. 두 개를 얹으면 총 처리량이 오르지만 슬롯당 속도는 반이 된다.

| | 슬롯당 fps | 합산 | 배치 소요 |
|---|---|---|---|
| 1잡 × 8장 | 35,214 | 281,712 | 3.1 h |
| 2잡 × 8장 | 18,833 | 301,332 | 5.8 h |
| 3잡 | 측정 비대칭(겹침 불완전) — 신뢰 못 함 | | |

운영 상한은 모든 트랙에서 **GPU당 2잡**이다. 빈 카드를 먼저 쓰고, 빈 카드가 없을 때만
메모리 여유가 26,000 MiB를 넘는 1잡 카드에 두 번째 잡을 얹는다. 공유 후보는 잡 수와
사용 메모리가 낮은 순서라 long·대형 잡은 가능한 한 혼자 남는다. 3잡은 금지한다.

## 8. 절대 하지 말 것

- **실행 중인 배치의 num_envs를 바꾸는 것.** 슬롯 간 비교가 깨진다.
- **실행 중인 bash 스크립트를 in-place 편집하는 것.** bash가 증분으로 읽어서 런이 죽는다.
  배치마다 새 복사본을 만든다. (전례: `train.sh` 수정 중 6개 런이 `unexpected EOF`로 사망.)
- **경고를 무시하는 것.** `rc=0`은 통과 조건이 아니다. `warn>0`이면 접촉을 버리고 있다.
- **검증 안 된 num_envs로 긴 학습을 거는 것.** 14 iteration 통과는 8시간 통과의 근거가
  못 된다. `scripts/steer/env_sweep.sh`로 격자를 재고, 후보는 최소 수백 iteration 소킹한다.

## 9. 실측 격자 (2026-08-17, steer carry · 단독 카드 · 40 iteration)

`envSpacing: 5` 로 바꾼 뒤 **세 축을 분리해서** 다시 쟀다. 이전 측정은 전부 `envSpacing: 0`
에서 잰 것이라 접촉쌍이 병목이었고, 그 상태의 숫자는 여기 없다.

### 9.1 접촉쌍 요구량 — `envSpacing: 5` 면 사실상 사라진다

버퍼를 **0.25 M 로 굶겨서** 로그의 `Capacity to N` 을 읽었다. 통과하는 값만 재면 요구량이
아니라 "그 이하" 까지만 알 수 있다.

| env | 요구량 | 0.25 M 에서 |
|---|---|---|
| 4096 | < 0.25 M | 통과 |
| 8192 | < 0.25 M | 통과 |
| 16384 | **0.3 M** | rc=1 |

`envSpacing: 0` 일 때 4096 요구량이 22.6 M 이었다. **90 배 넘게 줄었다.**

### 9.2 버퍼 크기 → 속도 (4096 env)

| `max_gpu_contact_pairs` | sfps | fps total |
|---|---|---|
| 32 M (지금 운영값) | 53,830 | 29,419 |
| 4 M | 58,512 | 30,720 |
| 1 M | **60,786** | **32,636** |
| 0.25 M | 57,203 | — |

작을수록 빠르다. 단, 같은 32 M 끼리 `envSpacing` 0(56,377) vs 5(53,830) 이므로
**`envSpacing` 자체에는 속도 이득이 없다.** 하는 일은 작은 버퍼를 쓸 수 있게 여는 것뿐이다.

### 9.3 env 수 → 메모리 · 속도

| env | 메모리 | sfps | fps total | 4096 대비 |
|---|---|---|---|---|
| 4096 | 17.9 GB | 60,122 | 31,783 | 1.00× |
| 8192 | 25.6 GB | 58,619 | 34,791 | 1.09× |
| **16384** | 42.8 GB | 87,627 | **42,442** | **1.33×** |
| 32768 | 74.4 GB | 37,101 | 26,644 | 0.84× ← 꺾임 |

**메모리는 직선이다: `≈ 8.0 GB + 0.00215 × env`** (16384 예측 43.2 / 실측 42.8 / 32768 실측 74.4).
32768 은 80 GB 카드에 들어가긴 하는데 처리량이 16384 의 63 % 로 떨어진다. **16384 이 봉우리다.**

> **4096 을 같은 설정으로 두 번 쟀더니 fps total 이 30,720 / 32,845 로 7 % 벌어졌다.
> 그게 노이즈 바닥이다.** 8192 의 +9 % 는 턱걸이라 확실하다고 못 하고, 16384 의 +33 %
> 만 노이즈를 넘는다.

### 9.4 잡당이냐 카드 합산이냐 — 결론이 갈린다

16384 은 42.8 GB 라 **카드당 1 잡**이다. 4096 은 2 잡이 올라간다.

| | 잡당 fps | 카드 합산 fps | 카드당 슬롯 |
|---|---|---|---|
| 4096 × 2 잡 | 17,080 | 34,325 | 2 |
| 16384 × 1 잡 | **42,442** | 42,442 | 1 |

**카드 합산은 +24 % 뿐인데 잡당은 2.5 배다.** 그래서 이건 속도 문제가 아니라 배분 문제다:

```
시드 스윕처럼 여러 개를 나란히   →  4096 × 2 잡 (슬롯 12 개)
긴 학습 하나를 빨리             →  16384 단독 (2.5 배)
```

`f17_c12_long`(25000 iter) 기준 **52.7 h → 21.4 h**.

### 9.5 권장값

```yaml
envSpacing: 5                      # 0 → 5. 이게 접촉쌍 문제를 없앤다
max_gpu_contact_pairs: 4194304     # 4 M. env 수와 무관하게 하나로 통일
num_envs: 4096                     # 기본. 긴 단독 학습만 16384
```

**버퍼는 4 M 하나로 통일한다.** 16384 요구량 0.3 M 의 13 배이고, 1 M 대비 속도 손해는
4096 에서 3.7 % 다. env 마다 다르게 주면 num_envs 를 바꿀 때 같이 계산해야 할 항목이
하나 더 늘어나는데, 그 대가가 3.7 % 이면 통일이 싸다.

> **`STEER_CELL` 은 삭제 가능하다.** `envSpacing` 이 캐릭터까지 흩뿌리므로
> `_FlatTerrain` 의 수동 흩뿌림은 중복이다 (spacing 30 + CELL off 가 통과했다).

### 9.6 이 격자의 한계

- **16384 의 버퍼 축은 못 갈랐다.** 8 M 에서 87,627, 1 M 에서 66,619 가 나왔는데
  1 M 측정은 옆 카드에서 32768 런이 74 GB 를 쓰며 돌던 중이었다. 카드는 달라도 host CPU
  를 나눠 쓰므로 §7 의 "동거 상대가 바뀌면 비교가 깨진다" 가 그대로 적용된다.
  **다시 재려면 다른 트랙 큐를 비우는 게 아니라 GPU 권한으로 카드를 독점시킨다** (`plan/PLAN.md` GPU 배치).
- **학습 중립성은 아직 미확인이다.** 여기 숫자는 전부 처리량이고, 성적이 같은지는
  `f18_sp5`(spacing 0→5)와 `f19_e8192`(env 2 배)가 답한다. **그 전에 적용하지 않는다.**
