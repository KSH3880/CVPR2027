# 함정 목록

steer 에서 실제로 터진 것만 적는다. **결론이 아니라 재발하는 실패 방식**이 여기 있다.
ma 를 포함해 새 실험을 시작하기 전에 이 파일을 먼저 읽는다.

한 줄 요약: **이 프로젝트에서 시간을 가장 많이 태운 것은 학습이 아니라 잘못된 측정이다.**
F8~F12 전체가 한 번 무효화됐고, F4 는 통째로 폐기됐다.

---

## 1. 학습과 평가가 다른 config 를 읽었다 — 가장 비쌌던 사고

학습은 `amp_humanoid_steer_carry_cp32.yaml`, 평가 스크립트는
`amp_humanoid_steer_carry.yaml` 을 읽고 있었다. 08-15 에 학습 config 에서 terrain
잔재를 걷어내면서 **평가 config 를 안 고쳤다.** 그 뒤 F8~F12 의 모든 수치가
학습한 적 없는 규칙으로 채점됐다.

| | 평가가 쓰던 값 | 학습이 쓰던 값 |
|---|---|---|
| `randomHeightProb` | 1.0 | 0.5 |
| `minBottomSurfaceHeight` | 0.5 | 0.0 |
| `contactBodies` | 발 + **정강이 + 허벅지** | 발만 |
| `eval.skill` | loco + loco_terrain 5:5 | loco 100 % |

정강이 접촉으로 에피소드가 종료됐는데 학습에서는 한 번도 벌점을 안 받은 접촉이다.
바로잡자 대조군 성공률이 **0.8501 -> 0.9192** 로 올랐고, **vel 축 결론이 뒤집혔다**
(조준 vel 이 "순손해"에서 "원본보다 나음"으로).

**방어**: 학습과 평가는 같은 파일을 읽어야 한다. 지금은 `f2_eval.sh` 가 `_cp32.yaml`
을 직접 가리킨다. 새 파이프라인을 만들 때 **config 경로가 두 군데 하드코딩되면 그 자체가
버그**라고 보고, 한쪽만 고칠 수 있는 구조를 만들지 않는다.

## 2. 평가가 학습 설정을 재현하지 않았다

`STEER_TRAJ` 기본값을 v1 -> v2 로 바꾼 뒤, 이미 끝난 v1 정책 다섯 개를 v2 경로로
채점했다. 크래시가 없어서 몇 시간 뒤에야 발견했다 (`STEER_K=3` 은 shape 불일치로
바로 죽어서 오히려 다행이었다).

**방어**: `runs/queue/logs/<tag>.env` 사이드카. 학습 시작 때 환경변수를 전부 적고
평가가 그것을 `source` 한다. 사이드카가 없으면 `eval_one.sh` 가 **추측하지 않고
exit 5** 로 죽는다. 새 실험축을 추가하면 사이드카에 들어가는지 반드시 확인한다.

## 3. 같은 실험을 두 번 평가했다 (두 번 발생)

`needs_eval()` 이 아무도 안 쓰는 클레임 파일을 검사했다. 나중에는 손으로 띄운 평가가
클레임을 건너뛰었다. 같은 태그에 두 프로세스가 같은 로그와 같은 npz 를 써서
성공률이 두 개(0.8984 / 0.9102) 나오고 궤적이 섞였다.

**방어**: `eval_one.sh` 하나만 평가를 시작한다. `mkdir` 은 원자적이므로 그것으로
클레임을 잡는다. 자동이든 손이든 **같은 문 하나만** 쓴다.

## 3-1. 동일 tag 재사용이 구 종료 기록을 현재 실행으로 오인했다

ma 학습을 기존 tag로 다시 띄운 뒤 자동화가 같은 tag의 구 `exit.json`과 평가 로그를 읽어, 살아 있는 새 학습을 완료·실패로 조기 처리했다.

**방어**: 학습 시작 전 구 종료 표식을 제거하고 종료 판정은 현재 프로세스·평가 claim을 구 결과보다 먼저 확인한다. 출력 디렉터리가 있는 tag는 큐 투입을 거부하므로 재실행은 반드시 새 tag를 쓴다.

## 4. n=1 순위는 잡음이다 — F4 전체가 이것으로 폐기됐다

축별 승자를 한 번씩 재서 순위를 매겼는데, 나중에 재보니 **모든 차이가 한 설정의 자체
시드 산포 안**이었다. 측정된 값:

```
평가 뽑기 변동 (같은 정책, 다른 경로)   ±0.004   ← 작다
학습 시드 변동 (같은 설정, 새 학습)      0.046   ← 12 배
```

`f10b_head` 는 n=1 에서 +2.1 pt 로 승자처럼 보였다가 n=4 에서 베이스와 구분이
안 됐다. `f9_nat_pen06` 은 n=1 0.8105 -> n=4 0.7934 로 내려왔고 그 때문에 파레토
경계가 바뀌었다.

**방어**: 순위를 주장하려면 최소 n=4. 차이가 0.046 (학습 변동) 이하면 **시드를
늘리는 수밖에 없고, 평가를 더 해도 안 좁혀진다.**

## 5. 평가 하네스의 0 회차는 망가져 있다

`trans_players.py` 의 `num_repeat = 3` 은 **같은 평가의 3 회 반복**이다.
`ObjectSet_test_0/1/2` 라는 이름이 "물체 세트"처럼 보이지만 아니다.
그리고 **0 회차는 리셋이 안 가라앉은 상태**라 값이 낮다 (원본 stage2 terrain 은
0 회차가 0.0 이고 1·2 회차가 0.773/0.760).

`record_result.py` 는 `sum(r[1:]) / 2` 로 0 회차를 이미 버린다. 그런데 내가 로그를
직접 파싱해 분해할 때 3 회를 다 평균해서 원본 carry 를 0.5111 로 보고했다
(실제 0.7666). **하네스를 우회해 로그를 직접 읽을 때마다 이 규칙을 다시 적용해야 한다.**

## 6. npz 로그 창이 에피소드보다 짧다

`STEER_LOG=900` 인데 에피소드는 600 프레임이다. 창 경계에서 구간이 잘리고,
잘린 조각은 "박스를 들고 타겟으로 가는 중"으로 보여 **전부 실패로 집계된다.**
그래서 npz 로 계산한 대리 성공률(0.732)이 하네스(0.919)와 크게 벌어졌다.

완결 에피소드만 거르는 것도 안 된다 — **짧은(=실패한) 에피소드가 창에 더 잘 들어가서
반대로 편향된다.** 어떤 필터도 편향을 못 없앤다.

**방어**: 에피소드 단위 통계는 **하네스 수치만** 쓴다. npz 는 프레임 단위 관측
(속도 분포, 픽업 순간 정렬, 이탈 시계열)에만 쓴다.

## 7. 조건부 통계로 인과를 읽었다

"경로 길이 14 m 초과 구간에서 봉우리가 5.0 m 를 더한다" 고 보고했다. 길이가 긴 것만
골라놓고 쟀으니 **봉우리가 컸던 것만 뽑힌** 선택 효과였다. 생성기로 편향 없이 재보니
봉우리는 경로 길이 중앙값을 **0.46 m** 만 늘렸고, 완전히 없애도 14 m 초과가
26.7 % -> 20.2 % 밖에 안 줄었다. 그 위에 세웠던 "봉우리를 줄이자"는 추천을 철회했다.

**방어**: 결과로 조건을 걸고 원인을 읽지 않는다. 원인 쪽 분포를 **생성기에서 직접**
뽑아 비교한다.

## 8. 사후 추론으로 초기 상태를 알아내려 했다 — 세 번 틀렸다

"평가에서 박스가 바닥에 있는 비율"을 npz 로 재려다 세 번 틀렸다.

1. 에피소드 경계 프레임을 읽음 -> 카운터가 박스 텐서보다 먼저 증가해서 **직전
   에피소드의 들려 있는 박스**(z≈1.0)를 초기값으로 오인. "100 % 선반" 이라고 보고.
2. 픽업 전이에서 읽음 -> **재파지**(떨어뜨린 박스 다시 집기, 96 % 바닥)가 섞여 58 %.
3. 첫 픽업만 분리 -> 47 %. 설정값 0.5 와 맞지만 여전히 간접 추론.

결국 **리셋 시점 값을 스냅샷에 직접 기록**(`z0`)하고 나서야 끝났다. 기록값이 스텝
로그와 정확히 0.05 씩 차이 났는데, 그게 코드의
`self._box_states[ids, 2] += 0.05  # collision detection` 이라 검증까지 됐다.

**방어**: 알고 싶은 양은 **그 시점에 직접 기록한다.** 사후 추론은 세 번 틀릴 수 있다.

## 9. 지표가 실패 모드가 아니라 다른 것의 함수였다

- `delivered_frac` 은 표본이 10 개 미만이면 한 에피소드 비율이 그대로 나온다.
  `record_result.py` 가 `delivered_n < 10` 이면 공란으로 만든다.
- `early_place` 는 실패 모드가 아니라 `handoff` 의 함수였다.
- "타임아웃 비율"은 무의미했다 — `STEER_TERM=0` 이라 **성공해도 에피소드가 안 끝난다.**
  성공한 에피소드도 600 프레임을 다 돈다.

**방어**: 새 지표를 만들면 **대조군에서 먼저 재본다.** 대조군에서도 같은 값이 나오면
그 지표는 우리가 재려는 것을 안 재고 있다.

## 10. 판별자 점수는 런 간 비교가 불가능하다

AMP 판별자는 **태스크마다 새로 학습된다** (TokenHSI 논문 3.4: "We train a new motion
discriminator D from scratch during each task"). `ctrl` 의 logit -1.630 과 `pen06`
의 -1.696 은 **서로 다른 판별자가 매긴 점수**다. 내가 이걸 비교해서 "조종이 동작을
망가뜨린다"고 보고했는데 무효다.

덧붙여 **대조군도 99.53 % 로 판별당한다.** 판별자 정확도가 높은 것은 이 셋업의
기본 상태지 우리가 망가뜨린 결과가 아니다. 논문도 판별자 점수를 평가 지표로 안 쓴다
(표 1·2 는 성공률과 오차 cm 만).

## 11. `view` 를 `reshape` 으로 통과시키면 의미가 바뀐다 (ma)

`(E, num_actors, D)[:, :A]` 를 `(E*A, D)` 로 평탄화하려다 `view` 가 거부했다.
`reshape` 으로 바꾸니 크래시가 사라졌는데 **복사본이 만들어졌다.** 이 텐서는
IsaacGym 메모리를 가리키는 창이어야 해서, 복사본이면 리셋에서 쓴 값이 시뮬에 안 가고
갱신된 값도 안 읽힌다. **크래시 없이 조용히 틀린다.**

평탄 인덱스 `i = e*A + a` 의 메모리 오프셋은
`(i // A) * num_actors * D + (i % A) * D` 로 **i 에 대해 선형이 아니다.**
어떤 stride 조합으로도 표현할 수 없다. `num_actors == A` 일 때만 성립한다.

**A=1 회귀가 세 번 통과했는데도 A>=2 에서 무너졌다** — `[:, :1]` 은 크기 1 차원이라
언제나 병합 가능하기 때문이다.

**방어**: `reshape` 이 `view` 를 구제하면 멈추고 이유를 확인한다. 그리고
**A=1 회귀 통과는 A>=2 정당성의 근거가 아니다.**

## 실험 하나를 시작하기 전 체크리스트

1. **학습과 평가가 같은 config·같은 환경변수를 쓰는가** (사이드카 확인)
2. **대조군이 같은 배치에 있는가** — 다른 날 잰 값과 비교하지 않는다
3. **n 이 몇인가** — 순위를 주장할 거면 4 이상
4. **이 실험이 어떤 결과가 나와도 다음이 정해지는가** — 안 정해지면 설계가 덜 됐다
5. **새 지표는 대조군에서 먼저 재봤는가**

## 12. 환경변수 이름을 재사용해서 축 하나가 몰래 두 개가 됐다 (2026-08-18)

`f3_train.sh` 에 `envSpacing` 손잡이를 만들면서 이름을 `STEER_SPACING` 으로 붙였다.
**env 코드가 그 이름을 이미 쓰고 있었다** — `humanoid_steer_carry.py:76` 의
`self.steer_spacing`, 경로 창의 점 간격(기본 0.4 m)이다.

```
STEER_SPACING=5  →  envSpacing 5      (의도)
                 →  창 점 간격 5 m     (의도 안 함)
                 →  K=6 창이 2.4 m 가 아니라 30 m 를 본다
```

`f18_sp5`(13 h) · `f19_e8192`(10 h) · `f20_long16k`(13 h) 세 런이 통째로 무효.
결과가 이상해서(이탈 0.1345 → 0.3153, 성공률 0.887 → 0.650) 잡았지,
**그럴듯한 숫자가 나왔으면 그대로 결론으로 갔다.**

**방어책**
- 새 손잡이를 만들기 전에 `grep -rn "STEER_<NAME>" TokenHSI-steer/tokenhsi/` 로
  **그 이름이 이미 쓰이는지 먼저 센다.** 스크립트에만 없으면 되는 게 아니다.
- 스크립트 계층(train.sh)과 env 계층은 **같은 이름공간을 공유한다.** 학습 스크립트가
  export 하는 것은 전부 env 코드에 그대로 도착한다.
- 사이드카(`.env`)가 평가에 그대로 재생되므로 **오염이 학습과 평가에 똑같이 걸린다.**
  train/eval 이 일치한다고 해서 옳은 게 아니다 — 둘 다 같이 틀릴 수 있다.

같이 고친 것: 평가가 학습이 생성한 env cfg(`runs/gen_cfgs/steer/env_<TAG>.yaml`)를
쓰도록 `eval_one.sh` 가 `STEER_ENVCFG` 를 넘긴다. 사이드카는 `STEER_*` 변수만
되살리므로, cfg **파일**을 바꾼 런은 그것만으로 재현되지 않는다.


## 새 토큰을 붙였으면 gradient 부터 재라

`MA_TOKENIZER_ZERO=1` 처럼 "출력이 0 이어야 대조군과 같다" 는 초기화는 **마지막 층 뒤에
활성함수가 있으면 토크나이저를 영구히 죽인다.** `ReLU'(0)=0` 이라 backward 가 0 을
곱한다. ma·masteer 의 extra 토크나이저가 전부 이 상태로 수천 epoch 을 돌았고,
"토큰 효과 없음" 이라는 결론까지 나왔다 (2026-08-20 발견).

**이 버그는 끝까지 아무 신호도 안 낸다.** 학습은 정상으로 보이고 보상도 오르며
rc=0 으로 끝난다. 죽은 것은 새 토큰 하나뿐이라 나머지가 그 자리를 메운다.

    MS_GRADCHK=1 ... MS_ITERS=2   # 첫 backward 뒤 토크나이저별 |grad| 합을 찍는다

새 입력·새 토큰을 추가하면 2 iteration 짜리로 이것부터 돌린다. 체크포인트로도 잡힌다 --
학습 뒤에도 가중치 max 가 `1/sqrt(fan_in)` 과 정확히 일치하면 한 번도 안 움직인 것이다.

## 13. `CUDA_VISIBLE_DEVICES`가 Vulkan GPU를 제한하지 않았다 (2026-08-26)

Isaac Gym noVNC 뷰어를 `CUDA_VISIBLE_DEVICES=6`, `cuda:0`,
`graphics_device_id=0`으로 실행했는데 Python PID가 물리 GPU 0에도 그래픽
컨텍스트를 만들었다. CUDA/PhysX의 `cuda:0`은 마스킹된 물리 GPU 6을 뜻하지만,
Vulkan 장치 열거는 `CUDA_VISIBLE_DEVICES`와 독립적이다. 터미널에는 둘 다
`0`으로 보여서 화면과 시뮬레이션이 정상이어도 잘못된 물리 GPU 사용이 숨는다.

처음 넣은 PCI selector도 이 서버에서는 실패했다.

| selector | Vulkan에 노출된 장치 | 판정 |
|---|---:|---|
| `pci-0000_e6_00_0!` | NVIDIA 8장 + llvmpipe 1장 | 실패. `graphics_device_id=0`이 물리 GPU 0을 선택 |
| `6!` | UUID `8d9172bc-465c-1e5b-4240-28d6a045b785`, PCI `e6:00.0` 한 장 | 물리 GPU 6 |
| `7!` | UUID `3e1773be-ab91-d0cf-c707-a9ddeebdc342`, PCI `e7:00.0` 한 장 | 물리 GPU 7 |

**방어책**

- GUI·카메라·녹화는 가드가 연결된 트랙 `view.sh`·`record.sh` 또는
  `scripts/tokenhsi_gui.sh`로만 시작한다. 새 진입점도 Isaac Gym보다 먼저
  `scripts/vulkan_gpu_guard.py <6|7>`를 호출한다.
- 가드는 6·7 이외 번호와 `NODEVICE_SELECT`를 거부하고, 숫자형
  `DRI_PRIME=<GPU>!` 적용 뒤 Vulkan 장치 수가 정확히 1인지 검사한다.
- 그 한 장의 Vulkan UUID가 `nvidia-smi -i <GPU>`의 UUID와 다르면 Xvfb와
  Isaac Gym을 시작하지 않는다. 단순히 장치 수만 세면 잘못된 한 장도 통과하므로
  UUID 비교를 제거하지 않는다.
- `DRI_PRIME=pci-...!`와 `CUDA_VISIBLE_DEVICES` 단독 제한은 금지한다.
  `--graphics_device_id 0`은 가드가 성공해 Vulkan 장치가 한 장만 보일 때만 쓴다.
- 이 방어는 실행 프로세스의 환경변수만 설정한다. 서버 전역 Vulkan·드라이버 설정은
  수정하지 않는다.

수동 preflight는 GPU 작업을 시작하지 않고 다음처럼 확인한다.

    python3 scripts/vulkan_gpu_guard.py 6
    # stdout: 6!
    # stderr: physical GPU 6, UUID ..., DRI_PRIME=6!

## 14. pickup latch와 frame 평균이 시각적 놓침을 숨겼다 (2026-08-30)

mastop의 `pick`은 손 평균 위치·10 cm lift가 10 frame 연속이면 이후 영구히 1이고,
`heldStop`은 stop frame 전체 평균이었다. 잠깐 들었다가 놓치거나 resume 뒤 놓쳐도
`pick≈0.9`, `heldStop≈0.9`가 나와 GUI의 반복 실패와 수치가 모순처럼 보였다.

**방어책**
- latch 성공률을 terminal retention으로 부르지 않는다.
- 양손 각각의 box OBB 거리, terminal 상태, stop 이후 break/regrasp를 episode 단위로 함께 센다.
- 손 net contact force는 접촉 상대를 구분할 수 없고 합력이 상쇄될 수 있어 단독 gate로 쓰지 않는다.
- 정지 자연스러움은 접촉 발 planar speed, path-frame 횡속도, yaw-rate를 별도로 측정한다.
