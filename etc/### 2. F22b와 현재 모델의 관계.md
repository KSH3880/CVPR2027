### 2. F22b와 현재 모델의 관계

  f22b_long_c20_e25000은 현재 minimal_live가 직접 상속한 체크포인트가 아닙니다.

  - F22b: A=1, 고정속도 steering 기준
  - 현재 minimal_live: ckpt_stage1.pth에서 adapt 구조로 시작
  - HumanoidMAF22Carry: F22b 정책을 A=2 물리환경에서 진단하기 위한 호환 wrapper

  F22 wrapper는 teammate token을 추가하지 않고 F22의 289-D 입력과 checkpoint shape를 그대로 유지합니다. 구현은 TokenHSI-masteer/tokenhsi/env/
  tasks/adapt_interaction_skills/humanoid_ma_f22_carry.py:1에 있습니다.

  ### 3. 월요일에 고친 것은 별도의 top-camera 버그

  월요일 기록의 핵심은 모델 상속이 아니라 GUI가 물리 상태를 변경하던 문제입니다.

  동일 B checkpoint가:

  - A runner에서는 5/6 성공
  - B wrapper top-camera에서는 0/6, 전부 terminate

  여서 wrapper 상속이나 residual을 의심했습니다. 하지만 동일 seed actor parity trace에서 첫 actor 입력과 base action이 bit-exact했고, residual
  gate도 계속 0이었습니다.

  실제 원인은:

  1. follow camera는 substep마다 refresh_actor_root_state_tensor() 실행
  2. top camera는 _update_camera()에서 즉시 return
  3. 뒤의 _update_marker()가 stale tensor와 indexed setter 사용
  4. marker ID뿐 아니라 box/object/platform 실제 actor ID까지 같이 전달
  5. 이전 substep의 박스 상태가 다시 써져 중력 낙하의 절반이 취소됨

  실제로 box z 속도가:

  정상 A/follow: -0.326932 m/s
  문제 B/top:    -0.163480 m/s

  로 정확히 절반이었습니다.

  top-camera 분기에도 refresh 한 줄을 추가한 뒤 같은 B wrapper가 6/6 성공, 0/6 terminate로 복구됐습니다. 이 기록은 docs/
  HANDOFF_MASTEER_PICKUP_YIELD_2026-08-25.md:79에 있습니다.

  이렇게 전달하면 가장 정확합니다:

  > F22b 자체의 weight inheritance가 깨진 문제라기보다, 과거에는 동일 구조 이어학습에서 --checkpoint만 사용해 rl_games가 checkpoint를 조용히 무
  > 시한 문제가 있었습니다. 같은 구조 resume는 --checkpoint + --resume 1, adapt 구조 초기화는 --hrl_checkpoint로 구분해야 합니다. 월요일에 발견
  > 한 별도 문제는 top-camera가 stale root-state tensor로 실제 box actor 상태를 되쓰던 GUI 물리 오염 버그였으며, actor parity trace로 정책/체크
  > 포인트 문제와 분리했습니다. 현재 minimal_live는 adapt 방식으로 Stage1 로드 로그와 학습된 tokenizer weight를 확인해 같은 상속 오류가 없습니
