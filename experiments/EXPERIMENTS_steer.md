동시에 tokenizer weight까지 zero-init(`STEER_TOKENIZER_ZERO=1`)해서 토큰이 상수 0 벡터가
되게 한 변형도 같이 돌린다. 셋을 비교하면 "환경 차이 / 토큰 존재 / 토큰 랜덤성"이 분리된다.

구현: `amp_network_builder_transformer_adapt.py`에 `ablate_token_ids`와
`extra_tokenizer_zero_init`를 추가(기본값은 기존 동작 그대로, 환경변수로도 제어).
shipped 코드가 bias만 zero-init하고 weight zero-init은 주석 처리해둔 걸 스위치로 되살렸다.

## S2 1차 (17:35 배치) 결과 — 600 iteration은 너무 짧다

2048 envs, 600 iterations, steering 보상 없음. 학습 후 512 envs x 3으로 평가.

| lr | 마스킹 대조군 | 창 켬 |
|---|---|---|
| 5e-6 | 0.205 | 0.392 |
| 2e-5 | 0.403 | 0.444 |

해석: adapt 스캐폴드는 AMP 판별자가 새로 만들어져 학습되지 않은 상태로 시작한다.
초반에는 판별자 보상이 정책을 pretrained에서 끌어내리기만 하고 아직 재수렴하지 못한다.

- lr을 낮출수록 나쁜 것(5e-6 → 0.205)은 직관과 반대인데, 파괴 구간에서는

- 창의 유무는 여전히 큰 차이가 없다(보상이 없으니 당연).

**→ 결정: 밤 시간을 긴 학습에 쓴다.** lr 5e-5, 4000 iterations.

### 보상 재조준 구현

원본 `compute_carry_reward`의 속도 항은 상자→목표 방향으로 조준돼 있다:
`exp(-5·(1.5 - v_box·d̂)²)`, 가중치 2.0 x 0.2.

**방향 벡터만 경로 접선 t̂로 교체한다.** 항을 더하지 않으므로 보상 총량이 안 변하고
AMP 비율(0.5/0.5)도 안 건드린다. 구현은 두 방향의 항을 각각 계산해 차이만 더한다:

```
rew_buf += 2.0 * 0.2 * (vel_term(u) - vel_term(to_tar))
u = normalize(w·t̂ + (1-w)·to_tar),  w = clip((remaining - handoff)/0.5, 0, 1)
```

목표 근처에서는 w가 0으로 떨어져 원래 방향으로 복귀하므로 **steering이 placement를
방해하지 않는다.** 0.5m 이내 네이티브 placement 구간(`vel_r = 1.0`)도 그대로 둔다.

### 성공시 종료

상자가 목표 0.2m 이내에 10스텝 연속 머물면 에피소드를 끝낸다.
이유: 에피소드가 600스텝 고정이면 배달 후에도 보상이 계속 나와서 **빨리 끝내는 게 이득**이 되고,
우회를 시키면 손해가 된다. 방향을 아무리 재조준해도 이건 안 고쳐진다.
S0에서 곡률 0.45+에 배달이 무너진 것도 같은 원인으로 의심되므로 함께 풀린다.

전부 환경변수로 게이트되어 있어 기존 동작은 그대로다 (`STEER_REAIM`, `STEER_TERM`).

# S4 계획 — 보상 설계 비교 (사용자와 합의, 2026-08-13 21시)

## 배경: 왜 이 배치가 필요한가

S3에 넣은 재조준은 **경로 접선 방향**을 썼는데, 여기엔 복귀력이 없다.
경로에서 2 m 옆으로 나란히 가도 접선 방향은 맞으므로 만점이다.
S0의 무학습 규칙이 R² 0.99를 낸 이유는 target을 **경로 위의 점**에 놓았기 때문이고
(벗어나면 그 점이 경로 쪽에 있어 자동으로 당겨진다), 접선으로 바꾸면서 그 성질을 잃었다.

## 보상 4계열

| | 이름 | 수식 | 성격 |
|---|---|---|---|
| A | 접선 방향 | `exp(-5(1.5 - v·t̂)²)` | **속도 방향**. 복귀력 없음 |
| **B** | **앞의 점 향해** | `exp(-5(1.5 - v·û)²)`, û = 앞 점 방향 | **속도 방향** + 위치 암묵 포함 |
| C | 이탈 감점 | `-λ(1 - exp(-2·d_lat²))` | **위치**. 직접 명시 |
| D | B + C | | 방향 + 위치 |
| E | 진행도 | `exp(-5(1.5 - ds/dt)²)`, s = 호길이 | **경로 소화량**. 코너컷에 취약 → C와 짝 |

**전부 항을 더하지 않고 기존 carry 속도 항(가중치 2.0 x 0.2)을 대체**하므로 보상 총량 1.0이
유지되고 AMP 비율(0.5/0.5)도 안 건드린다. C만 예외로 항이 추가되는데,
**운반 중 죽어 있는 `walk_r` 0.2를 재활용**한다 (상자를 들면 root가 항상 0.5 m 안이라
`walk_r`이 만점에 고정돼 그래디언트가 0이다).

**A는 S3가 이미 4000 iter로 돌고 있으므로 S4에서 제외한다** — 같은 lr·iter라 나란히 비교된다.

## 입력 파라미터는 두 개뿐

```
점 개수 K,  간격 d   →   보는 거리 = K x d
```
- **거리축**: 얼마나 앞까지 볼까 (1.2 / 2.4 / 4.0 m)
- **해상도축**: 그 거리를 몇 점으로 (6 / 4 / 3)

**이번 배치는 거리축만 본다.** 해상도는 거리가 정해진 다음 배치로 미룬다 — 축이 많으면 못 읽는다.

## 슬롯 배치 (8)

| 슬롯 | 보상 | 입력 거리 | 가리는 것 |
|---|---|---|---|
| 1 | 없음 (토큰 마스킹) | — | **대조군** |
| 2 | **B** 앞의 점 | 2.4 m | 기본안 |
| 3 | C 이탈 감점 | 2.4 m | 위치만으로 되나 |
| 4 | D = B+C | 2.4 m | 방향+위치 |
| 5 | E+C 진행도+이탈 | 2.4 m | 다른 계열 |
| 6 | B | 1.2 m | 거리축 |
| 7 | B | 4.0 m | 거리축 |
| 8 | B + 성공시 종료 | 2.4 m | 시간 압박 제거 |

공통: lr 5e-5, 2048 envs, 4000 iters, 곡률 0.15.

## 결과별 다음 행동 (돌리기 전에 정해둔다)

- **B가 대조군(0.61)을 넘고 R²도 높다** → B 확정, 해상도축 배치로
- **B는 되는데 C/D가 더 낫다** → 이탈을 명시하는 게 낫다는 뜻. D 확정
- **전부 대조군 수준** → 보상이 아니라 **frozen attention이 새 토큰을 안 듣는 것**이 원인.
  다음은 트랜스포머 동결 해제 (원래 S4로 계획했던 것)
- **C 단독이 이상 행동** (경로 위에 서 있기 등) → potential-based 형태로 교체
  (`γΦ(s') - Φ(s)`, Φ = -k·d_lat). 정책 최적해를 안 바꾸는 것이 수학적으로 보장된다
- **거리 4.0 m가 나쁘다** → 먼 구간이 노이즈. online 단계(S5)에서 R을 넉넉히 잡을 근거가 된다

- **속도 프로파일 추종** (몇 초에 어디) — 시간 파라미터화를 일부러 버렸으므로 배제

### 학습 곡선을 보기 시작했다 (`scripts/steer/curves.py`)

지금까지 체크포인트 평가만 보고 학습 곡선을 안 봤다. tensorboard 스칼라를 뽑아보니:

| | epoch 3200 시점 |
|---|---|
| 에피소드 보상 | 420 → **605 (아직 상승 중)**, 최고 646 |
| value loss | 0.018 → 0.005 |
| KL | 안정 |
| **판별자 agent 정확도** | **0.995** |
| **판별자 demo 정확도** | **1.000** |

**두 가지 발견:**

1. **4000 iteration은 수렴 전이다.** 보상이 여전히 오르고 있다.
   TokenHSI 공식 stage2는 `max_epochs: 1000000`으로 사실상 수렴까지 돌린다.
   S2에서 "600은 파괴 구간"이라 배웠는데, **4000도 짧을 수 있다.**

2. **AMP 판별자가 완승했다.** 정책 모션과 진짜 모션을 99.5%/100%로 구분한다.
   판별자는 1.85M 파라미터를 새로 학습하는데 정책 쪽은 0.64M만 움직이니 불공정한 싸움이다.
   스타일 신호가 포화돼 정책에 거의 안 간다.

### 파라미터 회계 — "파인튜닝"이 아니라 "프리즈 + 어댑터"다

| | 크기 | 상태 |
|---|---|---|
| 트랜스포머 + self encoder + composer | 1.04M | frozen |
| 기존 task tokenizer | 2.73M | frozen |
| **steer tokenizer** | **0.05M** | 학습 |
| adapter (composer 잔차) | 0.59M | 학습 (zero-init) |
| critic | 3.19M | 신규 (액션 무관) |
| AMP 판별자 | 1.85M | 신규 |

**행동 경로에서 학습되는 건 0.64M뿐이고, 경로 입력을 담당하는 건 0.05M이다.**

### 중요: frozen은 TokenHSI 공식 레시피다

comp / adapt / longterm **세 빌더 모두** self_encoder, 기존 tokenizer, weight_token,
transformer_encoder, composer를 얼린다. 논문의 모든 stage2 결과가 이 방식이다.
그리고 `new_extra` 자리는 원래 **같은 스킬 + 추가 관측**(지형 높이맵)용이라
우리 용법(같은 스킬 + 경로 관측)과 구조가 동일하다. **오용이 아니다.**

→ 따라서 "frozen이 병목"이라는 가설은 약해진다. **"덜 돌렸다"가 더 유력하다.**
다음 배치는 이 둘을 나란히 놓고 가른다.


## S3 결과 (18:13~22:10, 4000 iteration 완주분)

먼저 끝난 3개. 전부 2048 envs, lr 5e-5, epoch 4001.

| run | 구성 | 최종 보상 | 최고 |
|---|---|---|---|
| s3_1_ctrl | 토큰 마스킹 (대조군) | 610.8 | 662.3 |
| s3_2_window | + 경로 창 (보상 없음) | 608.9 | 662.2 |
| s3_3_reaim | + **접선 재조준** | 606.6 | 656.7 |

**셋이 사실상 동일하다.** 창을 넣어도, 접선으로 재조준해도 변화가 없다.

두 가지가 동시에 확인된다:
1. **창만 있고 보상이 없으면 정책은 그걸 무시한다** (s3_1 ≈ s3_2). 예상대로다.
2. **접선 재조준은 작동하지 않는다** (s3_2 ≈ s3_3). 접선은 복귀력이 없어서
   경로에서 나란히 벗어나도 만점이라, 사실상 아무 제약을 걸지 않는다.
   사용자가 설계 단계에서 지적했던 그대로이고, 이제 학습 결과로 확인됐다.

**공통 관찰**: 셋 다 보상이 여전히 상승 중이고(최고치가 마지막 구간에 있음),
판별자는 agent 0.995 / demo 1.000으로 완승 상태다. value loss는 0.015 → 0.005로 잘 떨어졌다.

## 내 구현 오류 정정 — xtrack은 "재활용"이 아니었다

사용자에게 "이탈 보정 항은 죽은 `walk_r` 예산 0.2를 재활용하므로 보상 총량이 유지된다"고
설명했는데, **구현은 그렇지 않았다.**

```python
# 틀린 구현
self.rew_buf += self.steer_xtrack * held * (on_path - 1.0)   # walk_r은 그대로 둔 채 페널티만 추가
```

`walk_r`을 빼지 않고 페널티만 위에 얹었다. 총량이 1.0 아래로 내려가서
task:disc 비율(0.5/0.5)이 task 쪽으로 줄어드는 왜곡이 생긴다.

**수정**: `compute_walk_reward`는 root가 상자 0.5 m 안이면 속도항을 1.0으로 고정하는데
(운반 중에는 항상 참), 그 구간에서만 상수 1.0을 `on_path`로 **교체**한다.

```python
pinned = ||box_xy - root_xy||^2 < 0.5^2
self.rew_buf += 2.0 * 0.2 * xtrack * pinned * held * (on_path - 1.0)
```

`on_path = 1`이면 기존과 동일하고, 벗어날수록 깎인다. 총량 상한 1.0이 유지된다.

이 버그를 안고 돌던 `s4_3_C_xtrack`은 중단했고, 같은 버그를 쓰는 `s4_4_D_both`,
`s4_5_E_progress`는 held/로 옮겼다. 수정 후 재투입한다.

## 재개(resume) 지원 확인

## S5 계획 (22:30 확정) — 공통 조상에서 갈라지는 보상 비교

### 왜 재개(resume) 방식인가

S3에서 두 가지가 확인됐다: (1) 4000은 수렴 전이다 (보상이 끝까지 상승),
(2) 접선 재조준은 작동하지 않는다 (대조군과 동일).

새로 8개를 처음부터 돌리면 또 4000에서 끊기고, 3.6시간을 적응 구간에 다시 쓴다.
대신 **`s3_2_window` @4000을 공통 조상으로 삼아** 거기서 보상만 갈라 이어 돌린다.

```
s3_2_window @4000  (창 있음, 보상 없음, 적응 완료)
        │
        ├─ s5_1  보상 없음        ← 길이 효과만 분리
        ├─ s5_2  B 앞의점 1.2m
        ├─ s5_3  B 앞의점 2.0m
        ├─ s5_4  C 이탈 (수정본)
        ├─ s5_5  D = B + C
        ├─ s5_6  E 진행도 + C
        ├─ s5_7  B + 성공시 종료
        └─ s5_8  B + disc_reward_scale 3
```

**모든 팔이 같은 조상에서 출발**하므로 차이는 전부 보상 탓이다.
그리고 `s5_1`이 "그냥 더 돌린 것"이라 **길이 효과와 보상 효과가 분리된다.**

- 총 12000 iteration까지 (4000에서 8000 추가), 2048 envs, lr 5e-5
- 소요 약 7.6시간 → 23:00 시작 시 06:40경 완료. 아침 여유 있음
- 재개는 검증 완료: epoch 4001 → 4002로 이어짐, 가중치·optimizer·frame 복원

### s5_8만 축이 다르다 (판별자)

S3 전 구간에서 판별자가 agent 0.995 / demo 1.000으로 완승했다.
TokenHSI 공식 레시피를 보니 물체 형태 적응(`stage2_object_*`)은
`amp_imitation_task_transformer_multi_task_adapt_disc3.yaml`을 쓰는데,
**adapt.yaml과의 차이가 단 한 줄이다**:

```
disc_reward_scale: 2  →  3     # 주석: "For better motion naturalness"
```

즉 판별자가 주는 보상의 크기를 1.5배로 키운다. 지형 적응은 2, 물체 적응은 3이다.
우리 disc_reward_mean이 0.42로 낮으니 이걸 키우면 스타일 신호가 살아날 수 있다.
`STEER_DISC3=1`로 배선했다.

### 결과별 다음 행동

- **s5_2/3(B)가 s5_1을 넘으면** → 앞의 점 방식이 작동. lookahead 거리를 좁혀 확정
- **s5_4(C)가 더 좋으면** → 이탈을 명시하는 게 낫다. D로 통합
- **전부 s5_1과 같으면** → 보상 문제가 아니다. 남은 후보는 frozen 용량과 판별자 포화.
  s5_8 결과를 보고 판별자 쪽이면 disc 축을, 아니면 동결 해제로
- **s5_8만 좋으면** → 판별자 포화가 주범이었다는 뜻. disc_reward_scale을 먼저 맞추고 재실험
- **s5_7(종료)은 보상값으로 비교 금지** — 에피소드가 짧아 누적 보상이 구조적으로 작다. 성공률로만

### 폐기한 것

`s4_*` 8개는 전부 held/로 옮겼다. 이유:
- `s4_1_ctrl`은 `s3_1_ctrl`과 동일 조건 (중복)
- `s4_3/4/5`는 xtrack 버그 위에서 돌던 것 (수정 후 s5_4/5/6이 대체)
- `s4_6/7`은 K를 바꿔 거리·점수·tokenizer 입력폭이 함께 움직이는 교란 설계였고,
  K가 바뀌면 `num_height_points = 2K`가 달라져 **재개 자체가 불가능**하다.
  거리축은 K 고정 + `STEER_SPACING`으로 다음 배치에서 다시 본다
- `s4_8`은 `s5_7`이 대체


## 운영 사고 2건 (23:15) — 둘 다 자초한 것

### 1. 실행 중인 셸 스크립트를 편집하면 그 잡이 죽는다

`s3_4_term`이 exit 2로 실패 처리됐는데, 로그 끝이
`train.sh: line 36: unexpected EOF while looking for matching '"'` 였다.
`bash -n`으로 검사하면 파일은 멀쩡하다. 즉 **파일이 깨진 게 아니라, 내가 `STEER_DISC3`
패치를 쓰는 도중에 실행 중이던 잡이 그 파일을 읽었다.**

bash는 스크립트를 한 번에 파싱하지 않고 **바이트 오프셋 단위로 조금씩 읽는다.**
실행 중에 파일 내용이 바뀌면 오프셋이 어긋나 문법 오류가 난다.

다행히 학습은 epoch 4001까지 완주했고 체크포인트도 정상이라 결과 손실은 없다.
**같은 편집으로 `s3_4_term`과 `s3_5_curv0.25` 두 개가 동시에 당했다** — 편집 순간
그 파일을 읽고 있던 잡이 전부 영향을 받는다.
`failed/`에서 `done/`으로 옮기고 사유를 기록했다.

**규칙: 잡이 실행 중인 스크립트는 제자리 편집 금지.**
고쳐야 하면 임시 파일에 쓰고 `mv`로 갈아끼운다(mv는 원자적이라 실행 중인 프로세스는
기존 inode를 계속 본다). 또는 잡이 없을 때 편집한다.

### 2. 체크포인트 경로를 디렉터리 목록으로 만들 때 파일이 섞였다

평가 잡 `e4k_s3_1_ctrl`이 `no such checkpoint:
output/steer/s3_1_ctrl/mid_s3_1_ctrl.pth/nn/Humanoid.pth`로 실패했다.
`os.listdir()` 결과에서 `[-1]`을 골랐는데, 내가 중간 평가용으로 복사해둔
`mid_s3_1_ctrl.pth` **파일**이 실행 **디렉터리**들과 같은 목록에 섞여 마지막으로 정렬됐다.

`if (d/x).is_dir()` 필터를 넣어 고쳤다.

**규칙: 산출물 디렉터리를 훑을 때는 항상 디렉터리/파일을 명시적으로 구분한다.**
같은 폴더에 임시 파일을 두면 반드시 이런 일이 생긴다.


### 같은 사고 3회 반복 → 운영 규칙으로 승격

`s3_4_term`, `s3_5_curv0.25`, `s3_6_k3` 세 개가 전부 같은 원인으로 `exit 2` 처리됐다.
셋 다 **epoch 4001까지 완주**했고 체크포인트도 정상이라 결과는 하나도 안 잃었지만,
실패로 잘못 분류될 뻔했다.

원인은 단 하나: 잡이 실행 중인 `scripts/steer/train.sh`를 제자리에서 편집한 것.
bash는 스크립트를 바이트 오프셋 단위로 읽으므로, 편집 순간 **그 파일을 읽고 있던
모든 잡**이 문법 오류로 죽는다. 한 번의 편집이 세 잡을 동시에 날린다.

**규칙 (앞으로 무조건 지킬 것)**

1. **실행 중인 스크립트는 절대 제자리 편집하지 않는다.**
2. 배치마다 스크립트 사본을 따로 둔다. S5는 `scripts/steer/train_s5.sh`로 격리했다.
   이제 `train.sh`를 고쳐도 S5는 영향을 안 받는다.
3. 꼭 고쳐야 하면 임시 파일에 쓰고 `mv`로 교체한다. `mv`는 원자적이고 inode를
   갈아끼우므로, 실행 중인 프로세스는 열어둔 기존 inode를 계속 읽는다.
4. **`exit 2` + 로그 끝의 `unexpected EOF`는 학습 실패가 아니다.** 체크포인트 epoch을
   먼저 확인하고, 목표에 도달했으면 `done/`으로 옮긴다. 자동 판별 로직을 루프에 넣었다.

### ma M0 착수 (02:00~)

steer가 5시간 이상 무인으로 안정적으로 돌아서, 계획대로 ma 인프라를 병행 시작했다.

설계 요점은 **A=1일 때 기존과 바이트 단위로 동일**하게 만드는 것:

```python
# humanoid는 매 env의 앞쪽 A개 actor 슬롯을 차지한다.
# 모든 humanoid 텐서는 agent 축을 가진 뒤 (num_envs * A, ...)로 평탄화된다.
# A == 1이면 shape이 기존 단일 에이전트 코드와 완전히 같다.
self._humanoid_root_states = self._root_states.view(
    self.num_envs, num_actors, 13)[:, :A].reshape(self.num_envs * A, 13)
```

같은 방식으로 dof(`[:, :A*num_dof]`), rigid body(`[:, :A*num_bodies]`),
contact force를 바꿨고, actor id는 `env_id*num_actors + a`로 A개씩 생성한다.
총 29줄 변경.

**평탄화를 고른 이유**: TeamHOI처럼 `(E, A, ...)` 축을 그대로 두면 학습 루프
전체를 고쳐야 한다. 평탄화하면 rl_games는 그냥 "env가 A배 많다"고 보게 되고,
A=1에서는 아무것도 안 바뀌므로 회귀 검증이 성립한다.

현재 A=1 회귀 테스트 실행 중(`ma_regress_A1.log`). 통과해야만 A=2로 넘어간다.

## F0. 전 구간 전환 (2026-08-14)

S0~S6은 경로가 **박스에서 시작**했다. 접근 구간은 pretrained policy에 맡기고 운반만 조종했다.
뷰어로 확인하다 드러났고, 사용자 지시로 전 구간(approach→grasp→carry→placement)으로 확장했다.
S계열 8개 학습런(s5_7, s6_1~5)은 경로 정의가 달라 의미가 없어져 중단했다.

### 경로 생성

`gen_full(root, box, target, curvature, seed)` — 두 leg 각각에 사인 급수를 옆으로 얹는다.

```
offset(t) = L · Σ_m c_m sin(mπt),   c_m ~ U(-1,1)/m
그 다음 급수 전체를 최대치가 curvature·L·U(0.2,1) 이 되도록 정규화
```

sin이 t=0,1에서 사라지므로 **세 점(사람·박스·목표)을 항상 정확히 지난다.** 이게 사인 기저를
쓰는 유일한 이유다. **턴 제한은 두지 않는다** — 박스에서 캐릭터가 멈추므로 그 코너는 공짜다.
(S계열 초기에 넣었던 전역 턴 제한이야말로 경로를 망가뜨린 원인이었다.)

정규화가 없으면 계수 합의 꼬리가 두꺼워 **한 번의 draw가 leg를 제 길이만큼 옆으로 밀어** 경로가
3배가 되고 저장 버퍼(32 m)를 넘는다. 테스트가 이걸 잡았다. 정규화 후 `curvature`의 의미가
"직선 대비 최대 옆쏠림, leg 길이 대비 비율"로 확정됐다.

### 위상 전환과 leg 마스킹

픽업 전에는 **root**를 접근 leg에, 픽업 후에는 **box**를 운반 leg에 투영한다.
전 구간 경로는 박스에서 되접히므로, 마스킹 없이는 운반 중인 박스가 접근 leg에 붙어
**호길이가 거꾸로 간다.** `project(xy, path, s_lo, s_hi)`로 leg를 제한한다.

검증 (512 env, test 모드 600 step, 픽업이 관측된 24 에피소드):

| 검사 | 결과 |
|---|---|
| 경로가 실제 박스 시작위치를 지남 | 중앙값 0.019 m, 최대 0.049 m |
| 접근 구간 호길이가 s_box 를 안 넘음 | 24/24 |
| 운반 중 호길이 역주행 | **0/24** |
| 픽업 직후 호길이 − s_box | 중앙값 −0.00 m (범위 −0.04~+0.03) |

### 측정된 경로 형상 (곡률 0.15, 2048 env)

| | 평균 | p90 | 최대 |
|---|---|---|---|
| 전체 길이 | 9.2 m | 14.6 m | 20.0 m |
| 접근 leg | 3.6 m | 8.8 m | 10.7 m |
| 운반 leg | 5.6 m | 9.5 m | 10.8 m |

저장 버퍼를 128(12.8 m)에서 **320(32 m)** 으로 늘렸다. 최대 20 m라 여유가 있다.

꺾임 통계는 **박스 코너를 빼야** 의미가 있다. 안 빼면 중앙값 85°/1.5 m가 나오는데
이건 코너 그 자체이지 leg가 걷기 힘들다는 뜻이 아니다. `path_stats`가 코너를 따로 보고하고
leg 통계에서 제외한다.

### 고친 버그 둘

**1. 보상 계수 2배 (S5까지 계속 틀려 있었음).**
adapt 환경은 `2.0·walk_r + 2.0·carry_r + handheld_r + putdown_r`이고 두 속도 항 모두
각 보상 안에서 0.1이다. 즉 방향 교체 비용은 `2.0×0.1 = 0.2`. S5까지 0.4를 썼으므로
**방향 교체가 아니라 순증**이었다(`−0.2·vel(원래방향) + 0.4·vel(경로방향)`).
0.2로 고쳤다. **D > B > C 순위는 F1에서 다시 확인해야 한다.**

**2. npz 스냅샷 desync.** `gt`/`final_tar`를 dump 시점에 통째로 저장했는데, 로그 버퍼가 찬
뒤에도 리셋은 계속되므로 **나중 에피소드의 경로가 앞 에피소드의 궤적과 짝지어졌다.**
크래시 없이 "추종이 나쁘다"로만 보인다. 실제로 이 때문에 접근 구간 검증이 3/19로 나왔고,
env를 의심해 리셋 순서까지 계측했지만 root/box/target 전부 **0.000** 이동 — 분석기가 틀린
것이었다. 리셋 시점에 로그가 아직 열려 있을 때만 경로를 별도 버퍼에 스냅샷하도록 바꿨다.
이제 구조적으로 어긋날 수 없다. 고친 뒤 같은 검사가 24/24로 통과했다.

> **교훈(재확인)**: 지표가 이상하면 지표를 먼저 의심한다. 이번이 두 번째다
> (첫 번째는 S3 분석기의 에피소드 선택 오류).

- `tokenhsi/utils/test_steer_path.py` — **42/42 통과** (전 구간·leg 마스킹 13개 추가)

## F1 폐기 → F2 (2026-08-14 오후)

F1(2048 env, 8슬롯)은 **1.4시간 돌린 뒤 버렸다.** 성능 때문이 아니라 그 위에서 돌던
물리가 접촉을 버리고 있었기 때문이다. 자세한 원인·측정은 [../docs/ENV_SCALING.md]에 있고,
여기에는 실험에 영향을 준 부분만 남긴다.

### 무엇이 틀렸었나

`_FlatTerrain.sample_valid_locations`가 zeros를 반환해서 **humanoid 전원이 world 원점에
겹쳐 섰다.** env 간 충돌은 collision group이 막지만 GPU broadphase는 겹치는 모든 AABB 쌍을
추적하므로, 요구 버퍼가 22배로 부풀어 PhysX가 `will miss interactions` 경고와 함께 접촉을
버렸다. **S2부터 F1까지 모든 steer 런이 이 상태였다** (로그 175개 중 79개에 경고).
공식 stage2 terrain carry 런은 같은 2048 env에서 경고가 0건이다 — 실제 지형이 캐릭터를
흩뿌리기 때문이고, 우리 평지 스텁만 이 조건을 만들었다.

env를 60 m 격자로 흩뿌리고 `max_gpu_contact_pairs`를 8M→32M으로 올려 해결했다.
지금 도는 F2 8슬롯은 **경고 0/8**이다.

### S 계열 수치를 어떻게 다룰 것인가

S0~S6의 성공률은 **접촉이 누락되던 시뮬레이터에서 나온 값**이고, 보상 계수도 2배 틀려
있었다. 순위 정보로만 참고하고 F 계열과 직접 비교하지 않는다. 체크포인트는 재개·비교
어느 쪽으로도 못 쓰므로 지웠다(S5만 기록용으로 남김).

앞 두 짝은 **성공률과 추종을 동시에 이긴다.** 세 번째만 `lat20` 이 추종에서 0.025

이유는 학습 곡선에 그대로 찍혀 있었다. `lat` 은 항 최대치의 94~97 % 를 **항상** 지급해서

27 % → 4 % 로 깎고 (AMP 보상 0.3783 → 0.3598, agent logit -1.63 -> -1.80),
(c) V(s) 가 "남은 수명"을 예측해야 해서 c_loss 가 2 배 (0.0107 -> 0.0211), 정규화된
어드밴티지에서 태스크 몫이 줄어 a_loss 가 절반 (-0.0194 -> -0.0094).
`latpen` 은 `lat` 에서 상수 c 만 뺀 것이라 **미분이 완전히 같은데** 위 셋이 전부 없다.

신호/노이즈로도 같은 결론이 나온다. `lat` 은 분자·분모가 같이 커져 c->inf 에서 2.38 % 에

`final_tar` 가 env 당 하나뿐이라 무효였다. **선반이 실패에 얼마나 기여하는지는 아직 모른다** —
하네스에 초기 박스 높이를 기록하게 해야 제대로 잰다.

### F12 선반 대응 — 실패. 원인 진단이 틀렸다는 뜻이다

`PIN_STEER` 는 조종 항이 박스 몇 m 안에서 지급을 멈출지를 정한다. 선반 충돌이
원인이라면 **같은 추종에서 성공률이 올라야** 한다. 실제로 나온 것은 추종을 포기한
만큼만 성공률을 받는 곡선이라 — 효율 1.32 / 2.68 / 2.91 — **계수를 낮춘 것과
구분이 안 된다.** `pin10` 은 두 축 모두 베이스보다 나쁘다.

"마지막 1~2.5 m 를 정책에 돌려준다"는 해법이 선반 문제를 못 겨냥한다. 원인이
진입 각도라면 각도를 제한해야지 조종을 끄는 것으로는 안 된다. **선반 기여도는
여전히 미측정이다** — 하네스에 초기 박스 높이를 기록해 높이별 성공률을 가르는 것이
남은 유일한 방법이고, npz 사후 추론으로는 세 번 실패했다.

### 평가는 박스를 100 % 올려놓는다 — 학습(50 %)과 어긋난다

`z0`(리셋 시점 박스 높이)를 스냅샷에 직접 기록하게 고치고 나서야 답이 나왔다.
사후 추론이 세 번 다 틀린 자리다.

| | |
|---|---|
| **평가(`--eval`) 리셋 박스 z** | 0.78 ~ 1.13, 중앙 **1.015**, **바닥 0.0 %** (n=1024) |
| 학습 config | `randomHeightProb: 0.5` — 절반이 바닥이어야 한다 |
| 뷰어(`--test`, `--eval` 없음) | 사용자가 바닥 박스를 봤다 |

기록값이 스텝별 박스 로그와 정확히 **0.050 씩** 차이 나는데, 이는 코드의
`self._box_states[ids, 2] += 0.05  # add 0.05 to enable right collision detection`
이 값이다. 즉 `z0` 는 물리가 내려앉기 직전의 **현재 에피소드 리셋값**이 맞다.

사용자가 뷰어에서 본 바닥 박스와 모순이 아니다 — `view.sh` 는 `--test` 만 주고
`--eval` 을 안 준다. **두 관찰 다 옳고, 모드가 다르다.**

`eval:` 블록은 `successThreshold` / `skill` / `skillInitProb` 만 덮어쓴다.
평가를 100 % 상승으로 만드는 코드 경로는 **아직 못 찾았다.** 사실만 확정이다.

무엇을 뜻하나:

- F8~F12 의 **모든 수치는 "박스가 100 % 선반 위" 조건에서 잰 것**이다. arm 끼리는
  같은 조건이라 비교는 유효하지만, 절대 성공률은 어려운 쪽만 재고 있다.
- 정책은 절반이 바닥인 분포로 학습하고 100 % 선반에서 채점된다. 성공률이 F5 의
  0.91 에서 0.78 로 떨어진 것의 일부가 여기일 수 있다 (초기 분포 변경 외에).
- 선반은 평가 에피소드 **전부**에 있다. 그런데도 `PIN_STEER` 가 안 통했다는 것은
  "마지막 구간에서 조종을 끄는" 해법이 틀렸다는 뜻이지 선반이 무해하다는 뜻이 아니다.

### 관측 위상 제거 — dual 이 이기지만 6000 에서 약해진다

남아 있던 것은 **관측**이다 — `_track()` 이 `held` 로 기준점을 고르는데, 운반 중
root-box 거리가 0.369 m 라 집는 순간 호길이 `s` 가 **0.393 m 점프**한다. 평상시
프레임당 0.0085 m 이므로 46 배이고 창 간격 0.4 m 와 거의 같다 -- 정책이 보는 K 개
점이 한 프레임에 통째로 한 칸 밀린다. 직후 이탈이 0.09 -> 0.16 (78 %) 튀고 1.3 초
뒤 가라앉는다.

세 가지를 시험했다:

| | 3000 결과 | 판정 |
|---|---|---|
| **창 2 개** (`STEER_DUAL`) — 래칫마다 창 하나씩, `held` 안 씀 | 0.8630 / **0.1428** | 채택 |
| **창 + 박스 스칼라** (`STEER_SLIM`) — `(_arc_box − _arc_root, lat_box)` 를 대신 줌 | 0.8279 / 0.1823 | **기각** |

그대로 주는 쪽이 우아하다고 판단했는데 **두 축 모두 최악이었다.** 겹치는 두 번째 창이
낭비가 아니라, 접근 중에 **운반 경로를 미리 보여주는 실질 정보**였던 것으로 보인다.

램프는 불연속만 없애고 위상은 남긴다. 이탈이 0.2494 로 오히려 나빴다 --
**불연속 제거만으로는 부족하고 위상 자체를 없애야 한다.**
